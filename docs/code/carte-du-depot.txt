CARTE DU DEPOT - KORA
(doc de code, pas de design de jeu)

A jour pour la version : 0.20.2
Mise a jour : 2026-10-16 (refaite : elle avait derive depuis 0.10 ; ses
sections 4, 8, 9 et 11 sont maintenant TIREES DU CODE).

Ce fichier dit OU vit le code, QUI appelle QUI, et OU aller quand on veut
changer quelque chose. Les parties entre "<<< auto" et "<<< fin auto >>>"
recopient les docstrings des modules, des outils et des tests, et la liste
des specs : python tools/notes.py write les refait ; pour les changer, on
change la DOCSTRING. Le reste est ecrit a la main et VERIFIE
(python tools/notes.py check, tests/test_notes.py) : chaque fichier, chaque
"module.nom" et chaque "Classe.champ" cite doit exister.

Ce que veut le joueur : docs/VISION-KORA.txt. Comment chaque chantier a ete
fait : les specs (section 11). Ajouter ou changer une fonctionnalite :
docs/code/ajouter-un-systeme.txt (la recette, et TOUTES les regles du code
par theme).


1. LIRE LE DEPOT EN 30 SECONDES
-------------------------------
  main.py              point d'entree : app.run ; une erreur est ecrite dans
                       %APPDATA%\Kora\kora_erreur.txt (avec la version)
  src/kora/            tout le jeu (section 4)
  tests/               les tests, sans fenetre (section 9)
  tools/               les outils (section 8)
  data/planetes/       les planetes cuites (<id>.json, <id>.png, index.json)
  data/kora_map.json   l'ancienne carte (768 x 384 ; les parties d'avant 0.20)
  data/fonts/, data/icons/, data/music/   polices, icones, musique (licences :
                       README, Credits)
  docs/                la vision, la charte, ce dossier code/, les specs
  Kora.spec, Kora-unfichier.spec   l'exe (dossier ; un seul fichier)
  .github/workflows/release.yml   une etiquette vX.Y.Z -> tests, exe, Releases,
                       itch.io
  empreinte.json       l'empreinte du jeu (tools/empreinte.py)
  .claude/settings.json   le crochet de debut de session (notes.py status)

  Le Python du projet : .venv/Scripts/python.exe (pygame-ce ; le Python du
  systeme a un autre pygame). Les tests : .venv/Scripts/python.exe -m pytest -q


2. LES DEUX MONDES : LA SIMULATION ET L'INTERFACE
-------------------------------------------------
  La SIMULATION (tout sauf l'interface) n'importe jamais pygame, ne lit
  jamais state.viewer, et tourne en Python pur (le multijoueur exige les
  memes nombres sur chaque machine). L'INTERFACE (app, render, render_*,
  theme, look, globe, globe_draw, layout, screens, tree_graph, music) lit la
  partie et ne la change QUE par un ordre (commands.py, via Play.issue).
  numpy : seulement globe_draw.py (le rendu) et mapgen.py (la cuisson des
  planetes, hors du jeu).
  Les ETAGES (qui peut importer qui) : docs/code/ajouter-un-systeme.txt,
  section 1 ; tests/test_architecture.py les verifie.


3. UNE IMAGE, UN PAS, UNE SEMAINE
---------------------------------
  Une IMAGE (Play._frame, ~60 par seconde) : en solo, sim.consume_ticks
  fait 0 ou 1 pas selon la vitesse ; en reseau, l'hote annonce les pas
  (session.py) et chacun les calcule ; puis les nouvelles (le journal du
  joueur), le survol, le dessin (Renderer.draw). Sauvegarde automatique
  toutes les 8 semaines.
  Un PAS (sim.tick) : une semaine, ou un jour quand une bataille touche un
  joueur (battle.slow). Une exception : l'etat d'avant revient
  (sim.snapshot), pause, state.last_error.
  Une SEMAINE (sim._week), dans cet ordre (le changer change le jeu) :
     1. clock (Clock.advance_week) ; une saison nouvelle se note
     2. sim.apply_season_spread   la saison locale avance par rangees
     3. sim.apply_movement        les marches (path, world.step_cost)
     4. sim.resolve_joins         les ralliements
     5. systems.WEEKLY            ost, sieges, grain, vivres des troupes
     6. learning.update_practice  le vecu (sols, hivers, rivages, steppe)
     7. battle : prune_fight_marks, resolve_raids, advance (les jours des
        batailles sans joueur)
     8. sim.update_exhaustion, sim.collect_food (collecte, faim),
        sim.remove_dead_bands
     9. sites.update              campements, caches, villages (semailles,
                                  recoltes, chantiers, troupes)
    10. chaque mois (tick_count % 4 == 0) : sim.update_population,
        population.monthly
    11. sim.update_influence ; chaque mois : systems.MONTHLY (dans l'ordre
        du tableau : diplomatie, commerce, production, chefferie, nombres,
        argent, chefs, approches, tournants, tirages, IA diplomatique,
        motifs de guerre, confederations, evenements, situations)
    12. events.weekly, sim.update_prestige, learning.update_learning
    13. vision.recompute_vision, memory.update, les ennemis apercus
    14. ai.decide_ai              les ordres de l'IA pour la semaine suivante
  Les ordres du joueur s'appliquent tout de suite (commands.apply), meme
  en pause ; ils ne passent pas par l'IA.

6. COORDONNEES ET ETAT EN MEMOIRE
--------------------------------
  Trois systemes de coordonnees, a ne pas melanger :
    Axial    Hex(q, r)       tout l'API public (Band.position, A*)
    Offset   (col, row)      le stockage, les fichiers ("odd-r")
    Sphere   lon/lat, xyz    globe.py seulement
  world.offset_to_axial / world.axial_to_offset ; wrap_x : les colonnes
  tournent, pas les rangees (les poles). World.distance et World.neighbors
  gerent le tour du monde ; world.hex_distance (brut) non.

  L'etat de la partie : gamestate.GameState (le monde, l'horloge, les
  peuples, les bandes, les lieux, la diplomatie, les journaux et vues des
  joueurs, les hasards : state.rng, state.story_rng, la graine des
  savoirs). Ses fiches : types.Tribe, types.Band, places.Site,
  places.VillageData (records.py les sauve d'apres leurs types). Le monde
  (world.World) garde les grilles lourdes (epuisement, influence, saison
  locale) : sim.snapshot ne copie que ce qui change.


7. DONNEES ET CODE
------------------
  La carte est de la DONNEE (comme chez Paradox) : une planete se cuit
  (tools/cuire_planetes.py : mapgen.py, numpy, quelques minutes) et se livre

  planete et se recharge dessus (persist.map_id ; l'ancienne carte :
  planets.LEGACY). Les regles sont du Python, avec leurs tests.

10. L'EXE ET LES CHEMINS
------------------------
  python -m PyInstaller --noconfirm Kora.spec   -> dist/Kora (le dossier
  entier : Kora.exe a besoin de _internal) ; Kora-unfichier.spec
  --distpath dist-unfichier -> un seul Kora.exe. Les deux embarquent TOUS
  les modules (KORA_MODULES) et data/ (planetes, ancienne carte, polices,
  icones, musique). Si Kora.exe tourne : WinError 5 ; ne pas reconstruire
  dist/Kora (le joueur l'utilise) : construire a part et le dire.
  Kora.exe en un seul fichier = DEUX processus (l'extracteur, puis le jeu) :
  pour arreter un essai, taskkill /T /F /PID (l'arbre), sinon le jeu reste
  orphelin et verrouille dist-unfichier/Kora.exe.
  Les parties : %APPDATA%\Kora\saves dans l'exe (saves/ dans le depot en
  developpement) : persist.saves_dir. JAMAIS toucher celles du joueur : les
  copier dans le scratchpad.
  Publier : __version__ (src/kora/__init__.py), commit, etiquette vX.Y.Z
  poussee : .github/workflows/release.yml fait le reste.

12. PIEGES CONNUS
-----------------
  - Un import de pygame "pour deboguer" dans la simulation casse les tests
    sans fenetre (test_architecture).
  - L'IA n'a pas de brouillard, le joueur si : dessiner une bande etrangere
    sans vision.enemy_band_visible = une fuite d'information.
  - path.astar a un plafond de noeuds : un ordre vers l'autre bout du monde
    peut echouer sans bruit. C'est voulu.
  - Un combat ne met jamais le jeu en pause et ne bouge pas la camera (P5).
  - Une bande en repli ignore les ordres : un test qui donne un ordre juste
    apres un combat laisse d'abord le repli finir.
  - World.hexes_in_radius et World.hexes_and_distances rendent des listes
    du CACHE : ne jamais les modifier.
  - World._season_frontier est une liste de RANGEES.
  - ai.decide_ai : une bande decide quand (tick_count + id) % 4 == 0 ; l'IA
    cherche un savoir une semaine sur quatre : un test choisit son tick.
  - Un village est une BANDE installee (Band.village) : les ordres de marche
    l'ignorent. Une troupe est une bande (Band.kind == "armee") : elle ne
    compte pas dans le plafond de bandes et ne se mele qu'aux troupes.
  - Une bataille a son propre hasard (battle._seed) ; les situations aussi
    (situations._rand) ; les tirages des savoirs (draws.py) ; une situation
    qui tirerait story_rng changerait tout l'equilibrage.
  - Les evenements ne tournent que si state.story est vrai (une vraie
    partie) : un test qui en veut le met a True.
  - diplo.frozen_relations : seulement autour d'une phase ou AUCUNE relation
    ne change.
  - L'influence est RECONSTRUITE chaque mois (influence.update) : ne pas
    garder une reference a une cellule.
  - famine_in_period est efface chaque semaine : lire Band.famine_tick.
  - Un monkeypatch d'une constante importee par nom ne touche pas la copie :
    lire module.CONST.
  - tools/accents.py sans --dry ECRIT (meme avec --help) ; il propose de
    faux accents ("Accepte" en tete de phrase, "l'a" / "n'a") : reformuler.
  - Un module appele seulement par systems.py n'etait pas dans l'exe : il
    l'est par KORA_MODULES (test) ; toujours essayer l'exe avant de publier.
  - soundfile plante en ecrivant un long OGG d'un coup (ecrire par blocs) ;
    les tests forcent SDL_AUDIODRIVER=dummy (conftest).
  - La cuisson des planetes : en avant-plan, ou un seul processus en
    arriere-plan (deux cuissons concurrentes s'etranglent).
  - Mesurer un ralentissement sur une copie du code (git worktree) : les
    sondes importent le code vivant ; une sonde de robot change avec le
    robot, pas avec le jeu.
